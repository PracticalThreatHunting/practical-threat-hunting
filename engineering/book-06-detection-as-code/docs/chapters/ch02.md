# Chapter 2: Write the Contract Before the Query

This is a cumulative study checkpoint in the edition, not a separate historical release.

## Artifact and proof scope

Case: two engineers implement the same request but disagree on entities, thresholds, time semantics, evidence, severity, and what should alert.

Build: versioned detections/DET-001/spec/detection.yaml containing observable behavior, inputs, invariants, exclusions, output fields, entity semantics, event/ingestion time, window/threshold, severity versus confidence, intended action, latency target, false-positive hypotheses, blind spots, and machine-testable acceptance cases. Define the runbook interface without writing an incident-response runbook.

Prove: schema validation; ambiguity review; executable examples; intentional invalid-contract tests.

## Exercises and answer criteria

1. Add a benign-looking case with `svc-maint` on `lab-maint-01` but a different change reference. Predict the signal key before running the evaluator. The case should remain positive because the three-field exception is a conjunction. Preserve it as a regression case if your implementation previously excluded it.
2. Propose a contract change that accepts events exactly at evaluation time. Identify the boundary case, fixture expectation, native predicate, and downstream overlap behavior that must change together. Explain why changing only the Python comparison would produce an inconsistent release.
3. Design a consumer contract for evidence that expires after a fixed retention period. Decide which fields must be preserved in the signal, which references can become unavailable, and how the consumer learns that evidence has expired. The answer should identify a retention dependency and a measurable failure mode, rather than assuming permanent access to raw records.

The answer distinguishes event identity, candidate identity, severity, confidence, required evidence, and exact endpoint semantics.
