# Chapter 7: SPL: Make It Native, Scheduled, and Actionable

This is a cumulative study checkpoint in the edition, not a separate historical release.

## Artifact and proof scope

Case: a literal translation scans raw data, double-counts events, ignores acceleration, and fails to create the expected finding/notable/risk output.

Build: equivalent native SPL for a declared Splunk Enterprise and Enterprise Security version; data/CIM requirements; tstats or raw search chosen with evidence; macros and lookup contracts; acceleration and summariesonly assumptions; schedule/lookback; deduplication/throttling; entity and finding/notable/risk fields; local tuning points; packaging metadata.

Prove: syntax and native execution; fixture positives/negatives; output fields; macro and lookup failure; accelerated versus nonaccelerated behavior where supportable; measured runtime. Present current contentctl and Detection Studio paths accurately and with dated support status.

## Exercises and answer criteria

1. Rename the logical-source field in a disposable adapter. Identify the native query, Sigma pipeline, extraction configuration, and evidence normalizer that must agree on the new mapping.
2. Design a lookup-failure test that distinguishes a missing file, an inaccessible file, a stale snapshot, and a duplicate key. State which failures should block complete output and which can produce a bounded degraded candidate.
3. Compare a raw baseline with an accelerated variant in an authorized environment. Record the eligible population, summary coverage, labels, repetitions, and result differences before comparing runtime. Explain which conclusions remain unavailable if acceleration is not licensed or configured.

The answer identifies raw-source mapping, lookup dependencies, runtime limits, and ES output action; acceleration is not assumed.
