# Chapter 18: Promote, Shadow, Canary, Roll Back

This is a cumulative study checkpoint in the edition, not a separate historical release.

## Artifact and proof scope

Case: an all-at-once enablement floods the SOC and cannot be reverted cleanly.

Build: delivery workflow from development to staging to production with separated privileges, protected environments, approvals, short-lived/OIDC credentials where applicable, shadow/monitor-only mode, canary scope, phased enablement, go/no-go criteria, alert-volume/latency/health rollback triggers, automatic and manual rollback, break-glass procedure, audit record, and post-release smoke tests.

Prove: dry-run, staged sandbox deployment, denied unauthorized promotion, rollback drill, and post-deploy state comparison. Never deploy into an unspecified tenant, index, or workspace; labs default to dry run.

## Exercises and answer criteria

1. Define a canary for DET-002 that could expose bucket-boundary and duplicate-volume failures. State which larger-population risks it cannot assess.
2. Write a rollback trigger that distinguishes an empty result from an absent scheduler execution. Identify its owner and evidence source.
3. Rehearse a rollback after an alert has already been delivered. Explain what the configuration rollback restores and what remains in the consumer's queue.

The answer defines authorized cohort, observation duration, quantitative stop conditions, prior state, and a rollback verification boundary.
